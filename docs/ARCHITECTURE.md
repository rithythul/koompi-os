# KOOMPI OS Architecture

Phase 1 specification. No implementation described here exists yet.

## 1. Base system

Debian stable (currently trixie), systemd init, mutable root. Normal `apt`
package management runs underneath; `vita` (see VITA_SPEC.md) is the only
user-facing package interface. Editions are profiles layered on this one
base — never forks (see EDITIONS.md).

## 2. Filesystem layout

Btrfs on GPT/EFI. Subvolumes, all mounted by name (never by subvolid, so
`snapper rollback` — which recreates subvolumes with new IDs — keeps
working):

| Subvolume     | Mount point  | In `@` snapshots? |
|---------------|--------------|--------------------|
| `@`           | `/`          | yes (the subject)  |
| `@home`       | `/home`      | no                 |
| `@var_log`    | `/var/log`   | no                 |
| `@var_cache`  | `/var/cache` | no                 |
| `@snapshots`  | `/.snapshots` | n/a (holds snapshots) |

`@home` and `@var_log` are excluded so that a rollback doesn't revert user
files or discard logs generated after the snapshot. `@var_cache` is excluded
because `apt`'s package cache is large, churns constantly, and has no
rollback value.

No swap partition. Swap is zram, managed by `systemd-zram-generator`.

## 3. Boot chain

1. UEFI firmware → GRUB (`x86_64-efi`) on the EFI System Partition.
2. GRUB reads `grubenv` for the boot-success fallback flag (§5) and either
   boots the default `@` root, or — if the flag says the previous boot
   failed — the recorded pre-update snapshot.
3. GRUB loads the kernel/initrd from `/boot` on `@`, passing
   `rootflags=subvol=@`.
4. systemd takes over: mounts `@home`, `@var_log`, `@var_cache`,
   `@snapshots` per `/etc/fstab` (by subvol name), starts zram, starts
   `grub-btrfsd`, reaches `graphical.target` (Plasma/Wayland via SDDM).
5. A oneshot systemd unit (`koompi-boot-success.service`), ordered after
   `graphical.target`, clears the fallback flag (§5).

grub-btrfs entries (submenu of past snapshots) are regenerated by
`grub-btrfsd` — see §4.

## 4. Snapshot orchestration: apt hook + grub-btrfs

### 4.1 apt pre/post snapshot hook

Debian's `snapper` package does **not** ship apt integration analogous to
its openSUSE/zypp hooks — that integration is zypp-specific upstream. KOOMPI
ships its own hook as a proper package, `koompi-snapper-hooks` (built in
koompi-repo, not sprinkled in by the installer), following the same
`DPkg::Pre-Invoke` / `DPkg::Post-Invoke` pattern used by Arch's `snap-pac`:

- `/etc/apt/apt.conf.d/80koompi-snapper` registers:
  - `DPkg::Pre-Invoke { "/usr/lib/koompi-snapper-hooks/pre-apt.sh"; };`
  - `DPkg::Post-Invoke { "/usr/lib/koompi-snapper-hooks/post-apt.sh"; };`
- `pre-apt.sh` runs `snapper -c root create --type pre --print-number
  --description "apt: <command line>"`, records the returned snapshot
  number in `/run/koompi-snapper-hooks/pre-number`.
- `post-apt.sh` reads that number and runs `snapper -c root create --type
  post --pre-number <n> --description "apt: <command line>"`.
- Hooks no-op (exit 0) if `/` is not on Btrfs or `snapper` is not
  configured, so the package is safe to have installed unconditionally.

This is orthogonal to `vita update`'s own pre/post snapshot pair (see
VITA_SPEC.md §5): the apt hook covers *any* apt invocation (including
direct `apt` use, Ansible-driven installs, etc.), while `vita update`'s
snapshots additionally bracket the flatpak update step and the
boot-success flag arming.

### 4.2 grub-btrfs

`grub-btrfs` is **not packaged in Debian's archive** (verified: no
`grub-btrfs` package in trixie's `packages.debian.org`). KOOMPI packages it
from upstream (github.com/Antynea/grub-btrfs) into koompi-repo — see
REPO_POLICY.md.

We use its upstream systemd path rather than the apt-hook-triggered path:
`grub-btrfsd --syslog` runs as a persistent service watching `/.snapshots`
via inotify, and regenerates the GRUB snapshot submenu whenever a snapshot
is created or deleted. This decouples menu regeneration from any single
snapshot producer (the apt hook, `vita update`, or a manual `snapper
create`) — one daemon, one inotify watch, correct for all of them.

## 5. Boot-success auto-fallback

Goal: if an update leaves the system unable to reach a working desktop, the
*next* boot automatically falls back to the pre-update snapshot without
user intervention.

### 5.1 Mechanism

Two GRUB environment variables in `grubenv`:

- `koompi_pending_snapshot` — snapshot number to boot if the flag is set.
  Written by `vita update` before it starts the apt transaction; cleared
  (unset) by the boot-success unit.
- `koompi_boot_pending` — `1` if an update is in flight or the post-update
  boot hasn't yet confirmed success; unset otherwise.

Sequence:

1. `vita update` calls `snapper -c root create --type pre --print-number`
   to get the pre-update snapshot number, writes it to
   `koompi_pending_snapshot` via `grub-editenv /boot/grub/grubenv set`, and
   sets `koompi_boot_pending=1`.
2. `vita update` runs `apt full-upgrade`, then `flatpak update`, then a
   `snapper create --type post` snapshot pairing the pre snapshot.
3. On next boot, GRUB's config (via a small custom grub.d snippet,
   `/etc/grub.d/41_koompi_fallback`) checks: if `koompi_boot_pending=1`,
   set the default boot entry to the grub-btrfs entry for
   `koompi_pending_snapshot` instead of the normal `@` entry, and continue
   as normal otherwise.
4. `koompi-boot-success.service` (`After=graphical.target`,
   `WantedBy=graphical.target`) runs `grub-editenv /boot/grub/grubenv unset
   koompi_boot_pending koompi_pending_snapshot` once the graphical target is
   reached. Reaching `graphical.target` is treated as success — SDDM
   starting and presenting a login prompt is a low bar, but is the same bar
   Debian's own boot health has to clear, and avoids inventing a
   heavier liveness probe for Phase 1.

### 5.2 Failure matrix

| Scenario | Behavior |
|---|---|
| Power loss mid-`apt full-upgrade` | `koompi_boot_pending` is already `1` from step 1. Next boot: GRUB detects the flag, boots the pre-update snapshot (which predates the interrupted transaction) instead of the possibly-corrupt `@`. User is on a known-good system; `apt` state in the *live* `@` may still be broken until they roll forward again, but they aren't stuck. |
| Kernel panic / boot failure on the new (post-update) boot | `graphical.target` is never reached, so `koompi-boot-success.service` never runs, so the flag stays set. Next GRUB start boots the pre-update snapshot. |
| New boot reaches `graphical.target` but the desktop is otherwise broken (e.g. black screen after login) | Not detected — SDDM reaching a login prompt is the success signal, not full desktop health. This is a known gap; manual `vita rollback` or manual GRUB snapshot boot is the recovery path. Documented as a non-goal for a deeper health check in Phase 1 (see §7). |
| Repeated failures (system never reaches `graphical.target` even on the fallback snapshot) | The fallback snapshot boots read-only from GRUB directly (grub-btrfs entry), independent of the flag machinery, so it does not loop through `vita update`'s flag logic again. If *that* snapshot also fails to reach `graphical.target`, the flag remains set indefinitely and GRUB keeps booting the same fallback snapshot — a manual `snapper rollback` from a live/rescue environment is needed at that point. Phase 1 does not implement a snapshot-generation counter or multi-snapshot fallback chain. |
| `vita update` itself is killed before step 1 (before `koompi_boot_pending` is set) | No flag was ever set — next boot proceeds normally into whatever `@` state existed. No fallback triggers, but also nothing was left inconsistent, since the apt transaction never started. |

## 6. Installer TUI sequence

`koompi-install` (Zig, same toolchain rules as vita — see VITA_SPEC.md §1)
runs from the live ISO session. It reads edition manifests, policies, and
overlays from `/usr/share/koompi-os/editions/<name>/` on the live
filesystem — `base/live-build/` config (Phase 4) is responsible for
copying this repo's `editions/` tree there when building the ISO.

1. Language (Khmer / English) — first screen, sets the language for every
   subsequent screen.
2. Keymap.
3. Locale.
4. Timezone.
5. Disk selection.
6. Destructive-partition confirmation (explicit, typed confirmation, not a
   single keypress).
7. Hostname.
8. User account + passwords (user + root, or user with sudo — TBD in
   Phase 3, not fixed here).
9. Edition selection (government / school / enterprise / dev / general).
10. Bootstrap via `mmdebstrap` (see §6.2 for why over `debootstrap`).
11. fstab generation (by subvol name, per §2).
12. `grub-install --target=x86_64-efi` + `grub-mkconfig`.
13. Enable systemd units: `grub-btrfsd`, snapper timers, `zram-generator`,
    `NetworkManager`.
14. Apply the selected edition's overlay + manifest (see EDITIONS.md).
15. Done — prompt reboot.

### 6.1 Khmer-in-TUI strategy

A framebuffer/Linux-console TUI cannot render Khmer script acceptably —
Khmer requires complex-script shaping (reordering, stacked consonants,
diacritic positioning) that no Linux console font renderer supports, and
kernel console fonts are single-cell bitmap fonts with no shaping engine at
all.

Chosen approach for Phase 1: **the installer TUI runs English-only**, in a
terminal (not the raw Linux console) launched from within the live Plasma
session — the terminal emulator and a fixed Latin+Khmer-capable font
(Noto Sans Khmer or equivalent, bundled in koompi-repo's font stack) *can*
shape Khmer correctly since Plasma's terminal stack uses a real text
shaping engine (HarfBuzz via Qt), unlike a bare framebuffer console.
Screen 1 (language selection) is the one screen guaranteed to render
correctly in both languages because it's short, static, and can be
pre-rendered as a bitmap/image rather than shaped live text if needed as a
fallback.

Risk flagged: if Khmer text shaping in the chosen TUI toolkit turns out not
to be reliable even inside the graphical terminal, the fallback is an
English-only TUI for Phase 1, with a Khmer-language first-boot OOBE
(out-of-box graphical experience, running under the fully-shaped Plasma
session after install) instead of Khmer in the installer itself. This
tradeoff should be re-evaluated once a TUI toolkit is chosen in Phase 3.

### 6.2 mmdebstrap vs debootstrap

`mmdebstrap` is chosen over `debootstrap`: it's roughly twice as fast, uses
`apt` internally (giving multi-mirror and security-mirror support for
free), and supports `SOURCE_DATE_EPOCH` for reproducible bootstraps —
useful for a fixed installer environment. Its limitation (no
cross-distro bootstrap without `apt`/`dpkg` present) doesn't apply here:
the installer always runs from a Debian-based live ISO, so `apt` is always
available. `mmdebstrap` is in Debian's own archive.

## 7. Non-goals (Phase 1 and this repository)

- **No immutable/image-based updates.** The root stays a mutable, normal
  `apt`-managed filesystem; Btrfs snapshots provide rollback, not an
  atomic-image update model (no A/B partitions, no OSTree, no dm-verity).
- **No KOOMPI Desktop Environment in this repository.** It is a separate
  repository; v1 ships stock KDE Plasma (Wayland) via Debian/koompi-repo
  packages.
- **No AD/FreeIPA integration in Phase 1.** Government/enterprise identity
  integration is out of scope until a later phase.
- **No deep post-boot health check.** The boot-success signal (§5) is
  reaching `graphical.target`; it does not probe SDDM/Plasma actually
  rendering a usable session.
- **No multi-generation fallback chain.** Only one pending pre-update
  snapshot is tracked at a time (§5.2).
